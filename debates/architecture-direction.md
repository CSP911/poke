# POKE 아키텍처 방향 — A vs B

---

## 방향 A: 엣지를 키운다 (스마트 엣지)

```
엣지 = 자체 처리 능력 보유 (라이브러리, 디코더, 렌더러)
허브 = LLM + 오케스트레이션만
```

### 장점

| # | 장점 | 설명 |
|---|---|---|
| 1 | 허브 부하 분산 | 무거운 처리를 엣지가 나눠 가짐. 허브 병목 없음. |
| 2 | 네트워크 의존 낮음 | 데이터를 안 가져와도 로컬에서 처리 가능. 오프라인 가능. |
| 3 | 엣지 자원 활용 | GPU, NPU 등 엣지 하드웨어를 최대 활용. |
| 4 | 레이턴시 낮음 | 로컬 처리 → 네트워크 왕복 없음. 실시간 가능. |
| 5 | 분산 컴퓨팅 자연스러움 | 각 엣지가 독립적으로 처리 → 스케일 아웃 쉬움. |
| 6 | 프라이버시 | 데이터가 엣지에서 처리 → 허브/클라우드로 안 나감. |

### 단점

| # | 단점 | 설명 |
|---|---|---|
| 1 | 엣지 복잡성 폭발 | 영상 디코더, 폰트 렌더러, 오디오 코덱... 사실상 OS 재발명. |
| 2 | 엣지마다 다른 능력 | 라즈베리파이에는 코덱이 되는데 다른 기기엔 안 됨. 파편화. |
| 3 | 업데이트 어려움 | 라이브러리 업데이트를 모든 엣지에 배포해야 함. |
| 4 | 엣지 최소 스펙 올라감 | 가벼운 IoT 기기에는 못 올림. 엣지의 문턱이 높아짐. |
| 5 | LLM이 알아야 할 것 증가 | "이 엣지에 어떤 라이브러리가 있는지" LLM이 알아야 코드 생성 가능. |
| 6 | 개발 기간 | 사실상 Linux/Android급 생태계 구축. 년 단위. |

## 방향 B: 엣지는 단순 출력기 (덤 엣지)

```
엣지 = 받은 바이너리를 하드웨어에 출력 (화면, 스피커, 센서)
허브 = LLM + 무거운 처리 + 데이터 관리
```

### 장점

| # | 장점 | 설명 |
|---|---|---|
| 1 | 엣지 극도로 단순 | 프레임버퍼 쓰기, 오디오 출력, 센서 읽기만. 코드 수백 줄. |
| 2 | 아무 기기나 엣지 가능 | 최소 스펙: TCP + 출력 장치. 가전, IoT, 임베디드 전부 가능. |
| 3 | 업데이트 불필요 | 엣지는 바뀌지 않음. "받아서 출력"만 하니까. |
| 4 | LLM이 단순 | "이 엣지가 뭘 할 수 있는지" 몰라도 됨. 데이터만 보내면 됨. |
| 5 | 빠른 개발 | 이미 거의 완성됨. 지금 POKE가 이 구조. |
| 6 | 프로토콜 표준화 쉬움 | IMG, AUDIO, TEXT 등 데이터 포맷만 정하면 끝. |
| 7 | 방향성 일치 | "앱 없는 세상" = 엣지에 로직이 없는 세상. |

### 단점

| # | 단점 | 설명 |
|---|---|---|
| 1 | 허브 과부하 | 모든 처리가 허브에 집중. 엣지 100대면 허브가 병목. |
| 2 | 엣지 자원 낭비 | GPU 달린 엣지인데 화면 출력만 함. 비쌈. |
| 3 | 네트워크 의존 높음 | 허브 연결 끊기면 엣지는 아무것도 못 함. |
| 4 | 대역폭 소모 | 영상 프레임을 매번 네트워크로 보내야 함. 4K 60fps = 1.5Gbps. |
| 5 | 레이턴시 | 허브에서 처리 → 네트워크 전송 → 엣지 출력. 실시간 어려움. |
| 6 | 프라이버시 | 모든 데이터가 허브를 거침. |

## 방향 C: 하이브리드 — 있으면 쓰고 없으면 허브가

```
엣지 = 기본은 덤(B). 능력 있으면 로컬 처리(A).
허브 = 엣지 능력 확인 → 가능하면 코드 보냄 → 불가하면 데이터 보냄
```

### 동작

```
[엣지 등록]
  enroll: { capabilities: ["framebuffer", "audio"] }           → 덤 엣지
  enroll: { capabilities: ["framebuffer", "jpeg_decode", "gpu"] } → 스마트 엣지

[허브 판단]
  "이 영상 재생해" →
    스마트 엣지: 영상 파일 전송 + 디코딩 코드 전송 → 엣지가 디코딩+출력
    덤 엣지: 허브가 디코딩 → 프레임 데이터 전송 → 엣지가 출력만
```

### 장점

| # | 장점 | 설명 |
|---|---|---|
| 1 | 유연함 | 엣지 능력에 따라 최적 경로 자동 선택. |
| 2 | 자원 최적화 | GPU 있으면 활용, 없으면 허브가 대신. 낭비 없음. |
| 3 | 점진적 확장 | B로 시작해서 필요할 때 A 능력 추가. |
| 4 | 네트워크 적응 | 빠르면 데이터 전송, 느리면 코드 전송. |

### 단점

| # | 단점 | 설명 |
|---|---|---|
| 1 | 허브 복잡성 | "이 엣지에 뭘 보낼지" 판단 로직 필요. |
| 2 | 프로토콜 복잡 | 같은 작업에 두 가지 경로. 테스트 2배. |
| 3 | 엣지 파편화 | 어떤 엣지는 되고 어떤 엣지는 안 됨. |

## 비교 요약

| 기준 | A (스마트) | B (덤) | C (하이브리드) |
|---|---|---|---|
| 엣지 복잡성 | 높음 | 최소 | 가변 |
| 허브 부하 | 낮음 | 높음 | 중간 |
| 개발 기간 | 년 단위 | 지금 | 월 단위 |
| 엣지 문턱 | 높음 | 최소 | 기본 낮음 |
| 네트워크 의존 | 낮음 | 높음 | 중간 |
| 자원 활용 | 최대 | 낭비 가능 | 최적 |
| 확장성 | 좋음 | 허브 병목 | 좋음 |
| 실시간 | 가능 | 어려움 | 조건부 |
| "앱 없는 세상" | 앱은 없지만 OS급 | 완전 앱 없음 | 앱 없음 |

## 현실적 추천

```
1단계: B로 시작 (지금 POKE가 이미 이거)
2단계: enroll에 capabilities 추가
3단계: 스마트 엣지가 등록되면 C로 자연 전환
→ B에서 시작하되 C로 갈 수 있는 구조로 설계
```
