# Motion safety — design

Status: design, validated in simulation (`sim/body/sim.py`, class `Safety`). Not yet in the kernel.

## Problem

Skills (movement programs) are generated by a language model, for a body it has
just discovered, and run immediately. A skill can be wrong in any way: jumps,
NaN, angles past the mechanical stop, oscillation that cooks a servo, a gait
that flips the body over. None of that may reach the motors.

The rule therefore cannot live in the skill, or in the hub. It has to sit
where no generated code can reach around it.

## Where it lives

```
 skill unit (EL0)          kernel (EL1)                    actuator resident (EL0)
 ────────────────          ────────────────────────────    ───────────────────────
 writes io->cmd[]   ──▶   motion_tick():                   owns the I2C / PWM
 (its own page;            1. copy cmd from skill page      capability; reads ONLY
  no I2C/PWM mapping)      2. safety_filter()        ──▶   the filtered targets
                           3. write filtered targets         from a kernel page
                              to the actuator page
```

This uses the capability model from phase 5:

- The **skill** is an EL0 unit whose address space contains its own image,
  stack and one shared `motion_io_t` page. It is never given the servo
  controller's I2C/PWM window, so it cannot drive a motor directly.
- The **actuator resident** (e.g. PCA9685 driver) gets the I2C window from its
  `device.json`, but reads targets only from a kernel-owned page it can map
  read-only. It has no say in what the targets are.
- The **kernel** is the only code that moves numbers from one to the other,
  and `safety_filter()` is on that path. Bypassing it would require a mapping
  the kernel never hands out.

## Rules (in order)

| # | Rule | Default | Why |
|---|------|---------|-----|
| 1 | Non-finite value → hold previous target | — | a NaN reaching a servo is undefined behaviour |
| 2 | Clamp to per-joint angle limit | ±1.2 rad, from `device.json`/discovery | mechanical stops, cable wrap |
| 3 | Rate limit | 6 rad/s per joint | hobby-servo speed; prevents current spikes |
| 4 | Tilt e-stop: head roll or pitch beyond limit → freeze all joints, skill parked | 80° | body flipping over |
| 5 | Saturation budget: if rules 2–3 fire on > X % of ticks for 2 s → stop skill, report | 20 % | a skill that only works by being clipped is asking for motion the body cannot do (see below) |
| 6 | Watchdog: no fresh `cmd` from the skill within 3 ticks → hold | 30 ms | skill hung or preempted too long |
| 7 | Manual e-stop: GPIO button / `poke stop` → freeze, refuse new skills until cleared | — | a person must always be able to stop it |

Freeze means "hold the last safe target", not "cut power": cutting servo power
drops whatever the body was holding up.

Rule 5 comes straight from the first simulated run: the 3-joint skill that
scored best was rate-limited 2,821 times in 10 s. It "worked" only because the
safety layer kept shaving its demands. On real servos that is heat and wear,
so the tuner must also penalise saturation, and the kernel must refuse it.

## What the hub may change

Limits come from the body's library entry and from discovery, never from the
skill. The hub may tighten them at run time (slower, smaller), never loosen
them past the library values without a physical-test record.

## Reporting

Every rule that fires is counted per skill (`clamped`, `rate_limited`,
`nonfinite`, `estop`, `saturation_stop`, `watchdog`) and returned with the run,
so the tuner can score against it and the hub can explain why a skill stopped.
